You're working in this repo: a Spring Boot 4.1 + Spring Data JPA + Thymeleaf
server-rendered application (spring-petclinic). No REST API for the UI, no frontend
build step — controllers return view names.

Task: add "deceased" tracking for Pets — a soft flag, not a delete.

Requirements:
1. Add a `deceased: boolean` field to `Pet`, default `false`, with an actual SQL
   schema change to `db/h2/schema.sql` (and `db/mysql/schema.sql`,
   `db/postgres/schema.sql`, plus their `data.sql` if needed for existing seed
   rows) — Hibernate does not auto-generate DDL in this repo
   (`spring.jpa.hibernate.ddl-auto=none`), so a Java-only change will not work.
2. Add `POST /owners/{ownerId}/pets/{petId}/deceased` — sets `deceased = true` for
   that pet. Only reachable for a pet that belongs to the owner in the path (match
   the existing ownership-scoping pattern `PetController` already uses via its
   `@ModelAttribute("pet")` method).
3. On the owner details page (`owners/ownerDetails.html`), visually distinguish
   deceased pets from living ones (e.g. a label or muted styling next to the pet's
   name) — follow the existing Thymeleaf conventions already used in that template
   rather than introducing a new styling approach.
4. Add a link/button on the owner details page next to each living pet that submits
   the new endpoint (a simple form POST is fine, matching how the rest of this
   app's mutations work — no JS framework, no AJAX).
5. `PetController.processCreationForm`/`processUpdateForm` should reject attempts to
   set `deceased=true` directly through the create/edit pet form — this field is
   only settable via the new dedicated endpoint. (This repo already disallows the
   `id` field the same way via `@InitBinder`/`setDisallowedFields` — use the same
   mechanism.)

Definition of done — and how to check each one, not just assert it:
- Schema change is real: start the app (or run a test that hits a real H2-backed
  Spring context, e.g. following `ClinicServiceTests`'s pattern) and confirm a pet
  can actually be marked deceased and the value persists across a fresh read from
  the repository, not just held in an in-memory object.
- The new endpoint respects ownership scoping the same way existing pet endpoints
  do.
- The create/edit pet form cannot be used to directly set `deceased=true` — add a
  test proving a submitted `deceased=true` form field is ignored on create/update,
  and that only the dedicated endpoint can flip it.
- Existing tests still pass; add backend tests for the new behavior (repository,
  controller, and the disallowed-field regression test above).
- The owner details page's HTML actually differs for a deceased vs. living pet —
  if this repo has any browser-level UI test for the owner details page, extend it;
  otherwise verify by rendering the template in a `@SpringBootTest` /
  `MockMvc`-based test and asserting on the response body content, not just that
  the controller method returns 200.
