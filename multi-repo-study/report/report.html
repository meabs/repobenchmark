DOCUMENTATION-LAYER STUDY — FINAL DESIGN & RECOMMENDATION

The Recommended Repo

Six documentation-layer designs, tested against the same codebase, the same three tasks, the same model, four rounds each — ending in one repo configuration built from what the other five proved and disproved, then validated against the same bar. Extended below to five genuinely different, real-world codebases, to find out how much of this holds up outside the one template it was designed on.

repo-baseline repo-agent-optimised skill v1 skill v2 skill v3 repo-agent-recommended
Recommendation

Ship the repo-agent-recommended layout: tiny AGENTS.md index + six task-scoped skills + OKF with rationale folded in, no separate tree of "why we built it this way" documents.

It is the only one of six tested configurations with no measured cost penalty anywhere. repo-agent-optimised—the always-loaded AGENTS.md plus a full set of separate rationale documents (ADRs, short for architecture decision records)—has a proven, sign-consistent +40.3% token cost on the simple-change task, holding in all four rounds. Nothing in repo-agent-recommended replicates that anywhere; its mean cost sits at or below baseline on all three task types.

It inherits skill v3's discovery behaviour exactly: across 24 sessions and 24 correct outcomes, the agent found the unmentioned AGENTS.md on its own and opened precisely the skill(s) each task needed — never more, never fewer. Correctness and comprehension quality are tied for perfect across all six configurations, so this choice costs nothing on the one dimension every design already wins.

Doubled to n=8 rounds against baseline specifically to stress-test this: still no penalty anywhere, and on two of three tasks a cost advantage now leaning real (7 of 8 rounds cheaper, p = 0.07) though not yet past the conventional bar for proven — see the extension section below.

Update, tested against five more real codebases: this design's layout — tiny index, task-scoped skills, OKF with rationale folded in — still stands as the recommendation. What no longer stands as stated is "never a cost penalty" as a universal property: on comprehension tasks it holds cleanly everywhere tested; on actual code-change tasks its effect turned out to be real but repo-dependent, a genuine win on some codebases and a genuine cost on others (up to +86% tokens on one). See External validity below for the full picture, including one real failure that traced to a gap in the documentation itself, not the codebase.

How the recommendation reads after the full review: the layout is unchanged, but it now comes with conditions. Expect a saving of roughly 20% in dollars on comprehension and about 10% on code changes, not "never a penalty"; one codebase cost 61% more on a complex change. Comprehension answers were as accurate as baseline (47 vs 46 out of 50). Treat every generated doc layer as unverified until an agent has worked from it, because three of five contained factual errors and one omission caused a failure. Check each layer for what the build enforces (formatters, sync tests) before relying on it, and re-measure on your own codebase. See What the raw data adds.

In plain termswhat's actually being compared — read this first

When an AI coding agent is dropped into an unfamiliar codebase and asked to make a change, it has to work out, on its own, what the code does and how to change it safely. This study is about one question: what should a codebase's own documentation for an agent look like, and does the shape of it change how much the work costs? Six different answers to that question were built into six copies of the same real, working application, and each was tested identically.

The three pieces used to answer it, in plain terms:

  • AGENTS.md — a single file at the top of the repository. It's the one thing an agent is expected to read first, before anything else. In the heavier designs it's a long page explaining the whole project. In the design recommended here it's deliberately tiny — a name and a one-line description for each of the other documents, nothing more, so the agent knows where to look without being forced to read everything.
  • OKF (Open Knowledge Format) — a set of short, structured pages that describe what things are and how they connect: this table holds this data, this part of the code talks to that part, this behaviour exists for this reason. Think of it as the reference manual for the codebase — you go there to understand something, not to be told what to type.
  • A skill — a short, focused how-to guide for one specific kind of job: "how to add a database field," "how to add a new web address (endpoint) the app responds to," and so on. Rather than one huge instruction manual covering everything, the recommended design splits this into six small guides, each labelled clearly enough that the agent can tell, from the label alone, whether it's relevant to the task in front of it — and open only the ones that are.

That splitting-into-small-pieces idea has a name used throughout this report: gradual disclosure. Instead of handing the agent everything up front (which costs time and money reading things it doesn't need), the codebase offers a short index and lets the agent fetch only the specific piece relevant to the task at hand. Some of the designs tested here also came with prompts that told the agent exactly where to look (called prescriptive below); others gave it no hints at all and simply waited to see whether it found the documentation on its own (called emergent below) — that distinction matters when reading the results, and is flagged wherever it applies.

Methodologywhat's measured, what isn't

"Tokens" are the units an AI model is billed in — roughly, chunks of text it reads and writes. "Input" tokens are what the agent reads (the prompt, the files it opens); "cached-input" tokens are input it's already seen recently and gets charged a lower repeat-read rate for; "output" tokens are what it writes back. Every number in this report is pulled directly from the AI provider's own record of each session (never the agent's own self-report of what it did), and dollar costs are computed from those real counts at the model's published standard rate — $0.20 per million input tokens, $0.02 per million cached-input tokens, $1.20 per million output tokens. Correctness is independently re-verified after every session, not taken on trust: a fresh migration and full backend test run on a clean database for the two coding tasks, and a manual check against the real source code for the comprehension task. Every comparison in this document is 4 independent repeats (rounds) per combination, and a result is only called real when it points the same direction in every single one — the same bar used throughout, not relaxed for any one design.

Two prompt regimes, not one. repo-agent-optimised and skill v1/v2 were tested with a prescriptive prompt that names the doc files up front ("start by reading AGENTS.md…"). Skill v3 and repo-agent-recommended use a prompt that is byte-identical to repo-baseline's — no mention of AGENTS.md, skills, or okf/ anywhere, including in the self-report template. Their discovery numbers below are genuinely emergent, not prompted. Keep this in mind reading the evolution table: the early rows and the late rows were not tested under the same instruction, by design — the whole point of the later rows is to find out whether the doc layer works without being pointed at.
One constant across every session in this study, all six configs: the execution machine carries a pre-existing, repo-independent skill catalogue (general-purpose workflow skills, unrelated to this codebase) that every session had equal access to regardless of which repo it ran against. It does not bias the comparisons below — it was present identically in every cell, baseline included — but "emergent discovery" here means discovery of this repo's own docs on top of that constant scaffold, not discovery from a completely blank agent.

Sign-consistency vs. baseline — the only comparisons that are provably real

Plain version: every design was tested against baseline four separate times (four rounds), because judging from one run could easily be a fluke. For each of those four tests: did this design cost more than baseline, or less? If the answer was the same all four times, that's a real pattern. If it flipped even once — cheaper three times, then more expensive the fourth — the result can't be trusted, because it didn't even hold up across our own four attempts; it's probably just noise, not the design mattering. Of every design-vs-baseline comparison in this study, only 2 of 18 gave the same answer all four times — both on the simple-change task, listed first below. Everything else flipped at least once: the averages look different, but that difference isn't proven.

n=8 extension — does doubling the rounds resolve recommended vs. baseline?

repo-agent-recommended wasn't sign-consistent against baseline on any task at n=4. Since that's the config actually being recommended, it was worth a stricter test: four more rounds each for repo-baseline and repo-agent-recommended, doubling to n=8 (a coin-flip effect has a 1-in-8 chance of landing all-same-sign at n=4, but only 1-in-256 at n=8 — a real pass at n=8 would mean something).

Cross-tool checkdoes any of this replicate with a different agent?

Everything above is one AI provider's CLI (codex exec, gpt-5.6-luna). A natural question: is "gradual disclosure" a property of that specific tool, or does it hold up under a different one? A small, single-round check with Cursor's CLI (cursor-agent, model auto — Cursor's own cost-efficient routing) against the same two prompts (understanding, simple change), the same two repos (baseline, recommended), same no-hint framing. This is one round, not four or eight — a directional check, not a proof, and auto doesn't disclose which underlying model it actually routes to, so there's no real-dollar cost figure here the way there is for every gpt-5.6-luna cell above.

Discovery replicates, but partially. Cursor found the unmentioned AGENTS.md on its own in all 4 cells, matching the flagship result. On the simple-change task it opened exactly the two correct skills (add-api-endpoint, verify-work) in both repos — matching Codex's precision exactly. On the understanding task, though, it opened three task skills that task doesn't need at all (every one of Codex's 8 understanding-task sessions correctly opened zero). External validity: five repositoriesdoes any of this hold up off the one template it was built on?

Everything above was tested on one codebase: the FastAPI + React template this whole doc-layer design was built for. That's a real limitation — a doc layer might just happen to suit that one project's shape. So the same idea was tested again, cold, against five real, independently-chosen open-source projects picked specifically to not resemble each other or the original: different languages, different frameworks, different ages, different architectural styles. For each one, a plain baseline copy and a repo-agent-recommended-style copy (tiny AGENTS.md index + task-scoped skills + an OKF knowledge bundle, no prompt hints, same emergent-discovery bar as the flagship result above) were built from scratch, and the same three-task framework — understanding, simple change, complex change — was run against both, once each, no prompted hints either.

Scope, stated plainly: this is one round per cell, not four or eight — the same directional-not-proof caveat as the cross-tool check above, deliberately traded against covering five genuinely different codebases instead of one codebase eight times. Read the per-repo numbers below as "what happened this time," and the cross-repo pattern as the thing actually worth trusting.

In plain terms — what actually generalized and what didn't

The comprehension result holds up well. On the pure-understanding task, recommended used fewer tokens than baseline in 4 of 5 repos, by a wide margin (−33% to −44%) — the one exception, the .NET microservice, was a mild loss (+17%), not a wash. This is the same shape as the single-repo result, and it's the part of the original claim that travels best: a well-built doc layer reliably makes "figure out how this thing works" cheaper, across very different codebases.

The code-change result does not hold up the same way. On simple and complex changes, the single-repo study's headline was "never a cost penalty, sometimes a real saving." Across five repos, that's no longer true as stated: python-api's complex task cost 86% more tokens with the doc layer than without it (both passed; the extra cost was reading, not testing — 95 read/search commands against 41 for baseline, while running the test suite fewer times, 8 against 12), while java-spring's complex task cost 64% less. Three of five repos favor recommended, two favor baseline, and the swings are large in both directions. The honest, narrower claim: a good doc layer's effect on an actual code-change task is real but repo-dependent, not a universal discount — and on unfamiliar codebases, either direction should be treated as plausible until measured, not assumed.

What the raw data addsanswer quality, real dollars, discovery, and where the extra cost came from

Everything above compares token counts and a pass/fail check. Going back through the raw run files turned up five things the headline numbers hide, and one of them corrects a gap in the study itself.

1. The cheaper understanding answers were not worse answers

Understanding cells were originally checked only for "an answer file exists", which cannot show whether being cheaper cost accuracy. So all 14 saved answers were graded afterwards against the real source code, question by question (2 = correct and precise, 1 = partly right or vague, 0 = wrong), by separate agent passes that read the answers unlabelled first. Each task includes one trap question designed to catch a confident wrong answer.

Cursor's four answers (two repos) scored 10 and 10 for baseline, 9 and 10 for recommended. The graders were agent passes with the source as ground truth, one point differences are within grader judgement, and two of the graders lost shell access part-way through and finished their checks by reading files. Read this as "no measurable accuracy penalty", not as a precise ranking.

2. The documentation itself contained mistakes, and mostly got away with it

The grading also checked each recommended repo's documentation against the code. Three of the five layers contained a factual error relevant to the tasks: the Django offer skill says to write a condition as a plain Python class (Oscar actually requires a proxy-model subclass) and to register it through the wrong mechanism; the React knowledge pages say the mock database persists to a file (it uses browser storage); and the Spring entity skill says to touch seed-data files only for required columns, when any new column breaks them. In two of the three cases the agents gave the correct answer anyway, apparently by checking the code. The exception is one Cursor answer on spring-petclinic, which stated the seed-data files did not need changes, the same understatement the skill makes. That connection is plausible, not proven, because the transcript does not show the agent reading that skill. This is the same lesson as the formatter failure, in milder form: machine-written documentation is wrong in small ways more often than it looks, and how much that matters depends on whether the agent trusts it or checks it.

A validity threat to be honest about. The graders also found that the recommended documentation states some of the answers to the test questions almost word for word (the trap answer for django-oscar, the fix for the React environment question). Whether deliberate or coincidence, both the documentation and the questions target each codebase's notable quirks, so part of the understanding saving may come from documentation that happens to anticipate these particular questions. Real questions are not known in advance. Treat the understanding saving as an upper bound.

4. Where the extra cost on django-oscar came from

On the complex task the recommended run made 114 tool calls against 62. Of those, 95 were reading and searching (baseline 41) and only 8 were test runs (baseline 12). So the documentation did not send the agent into more testing, it sent it into more reading, plausibly because the skill it followed described a mechanism slightly differently from how the code works (see section 2) and the agent had to reconcile the two. That explanation is a hypothesis; the data show the reading, not the reason.

5. Discovery replicated: 15 of 15

The original study's flagship finding was that agents find an unmentioned AGENTS.md and open the right skills unprompted. Counting real commands in the session transcripts (not the agents' own reports, which were blank in many cells), every one of the 15 recommended Codex cells opened the documentation layer within its first four commands (all but one within its second), and the skills opened matched the task (for example the eShop runs opened the order-command and status-transition skills, the legacy petclinic runs opened the controller and model-field skills). No baseline cell had anything to find. Discovery is not the weak point; the accuracy of what is discovered is.

When the documentation is wronga real failure, and what fixing it actually cost

Two of the thirty cells above failed their independent verification on first attempt, both on the same repo's recommended arm: spring-petclinic-recommended's simple-change and complex-change tasks. Both failures traced to the same root cause, and it's the single most important finding to come out of the five-repo run.

The doc layer's AGENTS.md and skills never mentioned two real, load-bearing conventions this specific codebase enforces: a build-blocking code-formatting gate, and a test that fails if a new user-facing text label is added to the default locale file without adding it to every other locale file too. Neither is exotic — both are visible in the repo's own pom.xml and test suite to anyone who looked — but the doc layer simply didn't surface them. The baseline arm, with no doc layer at all, passed both tasks cleanly: with no narrow, confident path handed to it, it explored broadly enough on its own to notice both conventions unprompted. The recommended arm, trusting the doc layer's narrower and more confident guidance, moved faster and skipped the exploration that would have caught what the doc layer itself failed to mention.

This is worth naming directly: documentation can make an agent overconfident. A good doc layer's entire value proposition is that it lets an agent take a shorter path instead of re-discovering the codebase from scratch every time. That is exactly what makes an incomplete doc layer dangerous in a way a missing one isn't — an agent with no guidance falls back on caution and broad exploration; an agent with confident, incomplete guidance has no signal that anything is missing, and no reason to look further than it's been pointed. A "recommended" doc bundle is not a one-time deliverable that's finished when it reads as plausible — it's only actually verified once something has genuinely tried to work from it and either succeeded or exposed a gap. This is the same warning the original study's OKF bundles already carry in their own frontmatter (every page ships generated: {by, at} and no verified claim, precisely because machine-written documentation is unverified until tested) — this is that warning actually cashing out in a real, measured failure instead of staying hypothetical.

Fixed, and re-run — both failures, before and after

The two missing conventions were added to the doc layer as a new verify-work skill, logged as a dated entry in the bundle's own change log (the same honesty convention as above — the fix is recorded as a correction to a real gap, not silently folded in as if it had always been there), and both failing cells were re-run against the fixed doc layer. Rationale, folded into the concept doc it actually belongs to

Auditing repo-agent-optimised's six architecture-decision records against the OKF bundle found four of six already fully duplicated as plain description — exact repetition across artifacts. The two that weren't were genuinely load-bearing: an agent "cleaning up" authenticate() could plausibly delete what looks like dead code. Both got a home inside the OKF doc for the router they belong to, instead of a seventh parallel file:

okf/routers/login.mdexcerpt — new section
## Why `/login/access-token` always takes about as long to fail

`backend/app/crud.py`'s `authenticate()` looks up the user by email; if none is
found, it still runs `verify_password` against a fixed `DUMMY_HASH` before returning
`None`. This is a deliberate timing-attack mitigation, not dead/wasteful code:
without it, a login against a nonexistent email would return faster than one
against a real email with a wrong password, letting response time be used to
enumerate valid accounts. If you're touching `authenticate()`, keep this call even
though its result is discarded.

This is exactly the fact the transcript sample above shows an agent citing back, unprompted, when reasoning about the login router.
